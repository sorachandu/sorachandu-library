## Fraction

### 非数状態の比較が整合しない

`frac(1,0)` と `frac(0)` について、`NaN > 0` と `0 > NaN` がともにtrueになります。
`operator>` を `!operator<=` としている一方、NaNと通常値の `<` と `==` が
両方falseになるためです。ローカル実行で再現しました。

また、NaNは全通常値と `<` の上で同値扱いになり、通常値同士は大小比較されるため、
NaNを含む場合はstd::sort等が要求する狭義弱順序も成立しません。

方針の候補:

- 通常の有理数だけを扱い、分母0・未初期化を許さない。
- NaNを残し、有限値より前または後へ配置する全順序を定める。
- 浮動小数点NaNのような比較にする。ただしNaNを含むソートには別の比較関数が必要。

### 入出力が範囲内でも中間積がオーバーフローする

比較では、分子・分母がいずれもlong longに収まっていても交差積が収まりません。

```cpp
frac a(4'000'000'000LL, 4'000'000'001LL);
frac b(4'000'000'001LL, 4'000'000'002LL);
bool less = a < b; // long longの交差積がオーバーフローする
```

加算も、約分後の結果が収まる場合に中間の分母積が収まらない例があります。

```cpp
frac a(1, 4'000'000'000LL);
auto b = a + a; // 正しい結果は1/2,000,000,000だが、中間の分母積がオーバーフロー
```

両方ともUBSanで再現しました。
比較には__int128の交差積、四則演算には事前約分・__int128の中間値が使えますが、
約分後の結果がlong longに収まらない場合の扱い（前提条件、assert等）も定める必要があります。
加えて、LLONG_MINに対するabsや符号反転の扱いも整理が必要です。

## Fast_PrimeFactrize

### Pollard法で正の大きな入力がオーバーフローする

`gcd(y - x + N, N)` の `+ N` により、x/y/Nそれぞれがlong longの範囲内でも
加算結果が上限を超えます。

```text
N = 9223372021822390277
  = 2147483647 × 4294967291
```

この入力の素因数分解を実行し、UBSanで次の加算のオーバーフローを確認しました。

```text
3275993507860902608 + 9223372021822390277
```

x/yを[0,N)内に保てば差y-xはlong longに収まります。
既存gcdは絶対値を取るため、不要な `+ N` を取り除く修正が候補です。
または差・加算をより広い型で計算する方法があります。

### 入力の前提条件がない

`prime_factorize(1)` は空配列を返しますが、0を渡すと
`prime_factorize(0)` → `pollard(0)=2` → 再び `prime_factorize(0)`
となり再帰が終了しません。これはコードからの確認で、実行はしていません。
競技用にはN>=1を前提として明記・assertする設計が自然です。

Miller–RabinとPollard法を組み合わせる方針自体を変更する必要があるという指摘ではありません。
まず対応範囲を正のsigned 64-bit整数と定め、上記の境界処理を直して検証する案です。
